# Porting Guide

How to merge, extend, and maintain these portable project instructions across multiple repositories.

---

## Quick Start

### Scenario A: Target project has NO existing commands

```bash
# 1. Copy everything
mkdir -p /path/to/target/.claude/commands
cp commands/*.md /path/to/target/.claude/commands/

# 2. Copy and customize config templates
cp templates/AGENTS.md /path/to/target/AGENTS.md
cp templates/CLAUDE.md /path/to/target/.claude/CLAUDE.md

# 3. Initialize agent memory
mkdir -p /path/to/target/.claude/agent-memory
touch /path/to/target/.claude/agent-memory/{MEMORY,learnings,review-feedback,common-mistakes,task-history}.md

# 4. Run /agent-readiness in the target to generate domain guidelines
```

### Scenario B: Target project has SOME existing commands

Follow the manual merge process below.

## Architecture

Understanding the layered structure is key to merging correctly.

### The File Hierarchy

```
target-project/
├── AGENTS.md                          # Agent-agnostic conventions (ALL AI tools read this)
├── .claude/
│   ├── CLAUDE.md                      # Claude Code-specific (imports @AGENTS.md)
│   ├── commands/                      # Slash commands (synced + project-specific)
│   │   ├── develop.md                 # <-- from template (generic)
│   │   ├── pr.md                      # <-- from template (generic)
│   │   ├── my-deploy.md              # <-- project-specific (you wrote this)
│   │   └── ...
│   ├── skills/                        # Skills (project-specific)
│   │   └── commit.md                 # <-- project-specific
│   └── agent-memory/                  # Agent learning (project-specific, gitignored)
│       ├── MEMORY.md
│       ├── learnings.md
│       ├── review-feedback.md
│       ├── common-mistakes.md
│       └── task-history.md
├── docs/
│   ├── security-guidelines.md         # <-- domain-specific (generated by /agent-readiness)
│   ├── testing-guidelines.md
│   └── ...
└── .coderabbit.yaml                   # Points CodeRabbit to docs/*-guidelines.md
```

### What Lives Where

| Content | File | Who Writes It | Tracked in Git? |
|---------|------|--------------|-----------------|
| Cross-cutting conventions | `AGENTS.md` | You or `/agent-readiness` | Yes |
| Build/test/lint commands | `.claude/CLAUDE.md` | You or `/agent-readiness` | Yes |
| Workflow commands (from template) | `.claude/commands/*.md` | Template sync | Yes (tracked) |
| Workflow commands (project-only) | `.claude/commands/*.md` | You | Yes (tracked) |
| Domain guidelines | `docs/*-guidelines.md` | `/agent-readiness` | Yes |
| Agent memory | `.claude/agent-memory/` | Agent (automatic) | No (gitignored) |
| CodeRabbit config | `.coderabbit.yaml` | `/agent-readiness` | Yes |

### Why This Separation Matters

- **AGENTS.md** is project-specific. Every project has different conventions. This file is the one agents read first to understand YOUR project. It should never be a direct copy from the template -- it must reflect the target project's actual patterns.

- **CLAUDE.md** is thin on purpose. It imports `@AGENTS.md` and adds only Claude Code-exclusive content (build commands, behavioral preferences). Most guidance lives in AGENTS.md where all AI tools can use it.

- **Commands are generic**. They reference "see CLAUDE.md for commands" and "see AGENTS.md for conventions" instead of hardcoding project details. This is what makes them portable. Project-specific commands (like a custom deploy workflow) live alongside them but ARE tracked in git.

- **Domain guidelines are generated**. Run `/agent-readiness` to scan your project and produce `docs/*-guidelines.md` files. These are deep, project-specific playbooks -- not generic templates.

## Manual Merge Process

For full control over the merge process.

### Step 1: Inventory What Exists

In the target project, check:

```bash
# What commands exist?
ls .claude/commands/ 2>/dev/null

# What config exists?
ls AGENTS.md .claude/CLAUDE.md CLAUDE.md 2>/dev/null

# What domain guidelines exist?
ls docs/*-guidelines.md 2>/dev/null
```

### Step 2: Classify Each Template Command

For each command in `project-instructions/commands/`, check if the target already has it:

```bash
diff project-instructions/commands/review.md target/.claude/commands/review.md
```

Classification:

| If... | Then... |
|-------|---------|
| File doesn't exist in target | Copy it directly |
| Files are identical | Skip (already synced) |
| Target version is simpler/shorter | Replace with template (it's likely an older version) |
| Target version has project-specific details | **Manual merge** -- see below |

### Step 3: Merge Customized Commands

When a target command has project-specific customizations (hardcoded repo names, specific tools, framework-specific patterns):

**Option A: Keep the customizations (recommended)**

The template commands are designed to defer to CLAUDE.md and AGENTS.md for project specifics. If a target command has inlined those details, you have two choices:
1. Move the project-specific details into AGENTS.md/CLAUDE.md (where they belong)
2. Replace the command with the generic template version
3. The command will now read project specifics from the config files instead of hardcoding them

**Option B: Extend the template command**

Add project-specific sections at the end of the template command, clearly marked:

```markdown
## Project-Specific Notes

- This project uses `tox` for testing: `pipenv run tox -e py312`
- Always check database is running: `pg_isready -h localhost -p 15432`
```

This approach works but creates merge conflicts on future syncs. Prefer Option A.

**Option C: Create a wrapper command**

If a project needs significantly different behavior, create a project-specific command that calls the template command:

```markdown
---
name: develop
description: Project-specific develop workflow
---
# Develop (Project-Specific)

Follow the standard `/develop` workflow with these project-specific additions:
1. Before starting: ensure Docker DB is running (`make start-db`)
2. Use `pipenv run tox -e py312-fast` for tests (not `make test`)
3. After implementation: run `make generate_v2_spec` if API changed
```

### Step 4: Set Up Config Files

**If target has NO AGENTS.md:**
1. Copy `templates/AGENTS.md` to target root
2. Fill in ALL bracketed placeholders (`[PROJECT_NAME]`, `[TECH STACK]`, etc.)
3. Remove irrelevant domain guideline rows from the index
4. Add project-specific conventions, anti-patterns, and testing patterns

**If target HAS an AGENTS.md:**
1. Compare structure. The template AGENTS.md has sections for: Domain Guidelines Index, Context Index, Key Conventions, Testing, Code Style, Commit Messages, What NOT to Do, Agentic Workflow Commands
2. Add any sections the target is missing
3. Add the Agentic Workflow Commands section listing available `/commands`
4. Do NOT overwrite project-specific conventions

**If target has NO CLAUDE.md:**
1. Copy `templates/CLAUDE.md` to `.claude/CLAUDE.md` (or repo root)
2. Fill in build/test/lint commands from the project's Makefile, package.json, etc.
3. Add any Claude-specific behavioral preferences

**If target HAS a CLAUDE.md:**
1. Ensure it has `@AGENTS.md` import (add if missing)
2. Check it doesn't duplicate content from AGENTS.md (move duplicates to AGENTS.md)
3. Keep only Claude-exclusive content (commands, behavioral preferences)

### Step 5: Track All Commands in Git

All commands -- both generic (from the template) and project-specific -- should be **tracked in git**. This ensures the autonomous agent always has every command available when working in the repo.

After copying the template commands, add them all:
```bash
git add .claude/commands/*.md
```

**Why track everything?** The agent loads commands from `.claude/commands/` at runtime. If commands are gitignored, they won't exist in worktrees, CI environments, or fresh clones. Tracking them guarantees the agent has the full command set in every context.

**Re-syncing**: When the template is updated, copy the updated commands and commit the changes. Project-specific customizations in the target repo will show as a diff during sync -- review and merge as needed.

### Step 6: Initialize Knowledge System

Set up the four-tier knowledge system (see [`KNOWLEDGE.md`](KNOWLEDGE.md) for full architecture).

**Tier 1 -- Rules directory** (tracked in git, grows organically):
```bash
mkdir -p .claude/rules
# Start empty -- patterns get added as the project matures
# Recommended starter files: architecture.md, patterns.md, testing.md
```

**Tier 2 -- Agent memory** (gitignored, for autonomous agent learnings):
```bash
mkdir -p .claude/agent-memory
cat > .claude/agent-memory/MEMORY.md << 'EOF'
# Agent Memory

Quick reference for patterns learned during development.
EOF

for f in learnings review-feedback common-mistakes task-history; do
  echo "# ${f//-/ }" > .claude/agent-memory/$f.md
done
```

Add to `.gitignore`:
```gitignore
.claude/agent-memory/
```

**Tier 0 -- Shared knowledge** (once, globally -- not per project):
```bash
mkdir -p ~/.claude/shared-knowledge
```

## Extending the Template

### Adding a New Command to the Template

1. Create the command in `project-instructions/commands/`
2. Use generic references (`see CLAUDE.md for commands`) instead of hardcoding project details
3. Add cross-references to related commands
4. Add it to the Command Inventory table in `README.md`
5. Add it to the Agentic Workflow Commands list in `templates/AGENTS.md`
6. Re-sync to target projects: copy the new command and `git add` it

### Adding a Project-Specific Command

1. Create the command in the target project's `.claude/commands/`
2. Do NOT gitignore it (it's project-specific, should be tracked)
3. You can reference template commands: "Follow the `/review` workflow, then..."
4. Add it to the project's AGENTS.md under Agentic Workflow Commands

### Modifying a Template Command for One Project

Don't modify the synced copy -- it will be overwritten on next sync. Instead:

1. **Preferred**: Put project-specific details in AGENTS.md/CLAUDE.md (the command reads from there)
2. **Alternative**: Create a project-specific wrapper command with a different name
3. **Last resort**: Modify the command directly and accept that syncs will show a diff to review

## Keeping Projects in Sync

### Manual Sync

```bash
# From the template directory
diff -rq commands/ /path/to/target/.claude/commands/ | grep -v "Only in /path"
```

Then copy updated files.

### Recommended Sync Frequency

- After adding new commands to the template
- After significant improvements to existing commands
- When onboarding a new project
- Quarterly review of all projects

## Troubleshooting

### Commands reference "CLAUDE.md" but mine is empty

The template commands say things like "see CLAUDE.md for the exact command." You need to fill in your project's actual build/test/lint commands in CLAUDE.md. Use `templates/CLAUDE.md` as a starting point, or run `/agent-readiness` to generate it.

### AGENTS.md is too generic

The template AGENTS.md is a starting point with placeholders. Run `/agent-readiness` in your project -- it will scan your codebase and generate project-specific conventions, or fill in the placeholders manually.

### A command doesn't work in my project

Most commands are framework-agnostic. They rely on CLAUDE.md and AGENTS.md for project specifics. If a command assumes something about your project that isn't true:
1. Check if the relevant info is in your CLAUDE.md/AGENTS.md
2. If not, add it -- the command should then work
3. If the command genuinely doesn't apply to your project, just don't sync it

### I want to customize a synced command

See "Modifying a Template Command for One Project" above. The preferred approach is to put project details in AGENTS.md/CLAUDE.md rather than modifying the command itself.
