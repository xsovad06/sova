# Workflow Rule History

Moved from `.claude/rules/workflow.md` (issue #1338), which keeps a short rule line per entry and points here: the full original text, with the incidents behind each rule.

## Rendered .agents/skills/

- **`.agents/skills/` is a rendered artifact of `sova/commands/data/commands/*.md` and `sova/commands/data/skills/*/SKILL.md`, exactly like `.claude/commands/`, but "managed" is no longer the same thing as "prefixed"**: every `sova-<name>/SKILL.md` (command-derived) and every bare `<name>/SKILL.md` matching a directory in `sova/commands/data/skills/` (standalone, e.g. `design-system`, `design-taste`, `issue-template`) is produced by `make skills-render` (`sova/commands/skill_render.py`) and guarded by `tests/test_skill_render_drift.py`, so a hand edit to either shape fails CI rather than vanishing silently, but it still must never be the place a change is authored (edit the canonical `sova/commands/data/commands/` or `sova/commands/data/skills/` file and re-render). Only `testing-patterns`, `database-patterns`, `dashboard-design`, and `visual-audit` are hand-authored, never touched by the renderer, despite also being bare names in that same tree (`testing-patterns` additionally exists in `sova/commands/data/skills/` as a generic standalone skill, but the renderer skips installing it here in favor of this repo's own more specific hand-authored copy already at that bare name; see `materialize_combined_skill_sources()`'s docstring, issue #1136).

## Unrendered .claude/skills/

- **`.claude/skills/` has no render step or manifest of its own**: unlike `.agents/skills/` and `.claude/commands/`, nothing regenerates it, so an entry with no SOVA-specific override must stay byte-identical to its `sova/commands/data/skills/` counterpart purely by discipline, guarded only by `tests/test_skill_render_drift.py::TestClaudeSkillsNoDrift` (today: `design-taste`). `issue-template` and `testing-patterns` are deliberate SOVA-specific variants (different prose, not just template substitution; see `tests/test_issue_template_skill.py`) and are expected to diverge from `sova/commands/data/skills/`. `dashboard-design`, `database-patterns`, and `visual-audit` are hand-authored with no `sova/commands/data/skills/` counterpart at all. CodeRabbit never reviews `.claude/**`, so a drifted identical-copy entry is invisible to anything but that test.

## Managed .claude/commands/ edits are reverted by sync

- **A `.claude/commands/` file edited directly (bypassing `sova/commands/data/commands/`) is silently reverted by the next sync**: every entry in `.claude/commands/.sova-manifest.json` marked `"managed": true` is treated as a rendered artifact of the matching `sova/commands/data/commands/*.md` template. If `.claude/commands/health-audit.md` or `.claude/commands/pr.md` gains functionality (a staleness check, a post-push self-review loop) that is never back-ported into `sova/commands/data/commands/health-audit.md`/`sova/commands/data/commands/pr.md`, the two drift silently: CodeRabbit's path filters mean nothing catches it, and the file looks correct for months. The next `sova commands sync` / `make marketplace` run then re-renders the SOVA copy from the stale canonical template, discarding the never-mirrored functionality with no error, no diff review, and no indication anything was lost: it reads as a routine sync, not a regression. Confirmed twice: a generic case flagged in PR #582 (dual-file pattern, `sova commands sync` overwrites SOVA customizations), and concretely on PR #1087 (issue #1028): an unrelated stdin-delivery PR's sync step silently reverted `.claude/commands/health-audit.md` by ~150 lines (losing the parallel 3-agent fan-out, staleness detection, and incremental-audit logic) and `.claude/commands/pr.md` by ~50 lines (losing the entire Post-Push CI+self-review section), both caught only by SOVA's own self-review since `.claude/**` is invisible to CodeRabbit. Fix in that instance: `git checkout origin/main -- <file>` plus restoring the matching `.sova-manifest.json` hash entries, since the changes were never part of the PR's actual scope. The durable fix is upstream of any single PR: any manual edit made directly to a `"managed": true` file under `.claude/commands/` must be ported into its `sova/commands/data/commands/` template in the same change, or it will eventually vanish without warning.

## Interactive Development Location

- **Do non-trivial work in a dedicated worktree, not the primary checkout.** The primary checkout should stay on `main`; every other active branch in this repo already lives under `.claude/worktrees/<issue-number>` (`git worktree list` shows the current set). An interactive session is not exempt just because no autonomous SOVA agent spawned it: on 2026-10-02 a full feature (5 commits, PR #1116) was developed and pushed entirely from the primary checkout before the user noticed and asked for it to be relocated. Before starting feature work: create the branch if it doesn't exist, then `git worktree add .claude/worktrees/<issue-or-topic> <branch>` and do all editing from that directory. If work already started in the primary checkout and the branch is pushed, it relocates losslessly: `git checkout main` in the primary checkout (frees the branch), then `git worktree add .claude/worktrees/<id> <branch>` to attach it elsewhere.

## Mirrored Command Pairs

- **Mirror changes across SOVA/distributable command pairs**: when a command exists in both `.claude/commands/` (SOVA-specific) and `sova/commands/data/commands/` (distributable), changes to shared sections must be applied to both files. CodeRabbit only reviews `sova/commands/data/commands/` (`.claude/` is excluded via path filters), so inconsistencies in the SOVA variant go undetected. After editing one, always diff the pair.

## Fenced Bash Blocks

- **Each fenced bash block in a markdown command runs in its own shell**: a variable or function set in one block is gone in the next (an unset `$PR_NUM` once posted a CodeRabbit trigger with no PR number). Every later block that uses a value re-derives it from durable inputs (PR number, `gh pr view`, `headRefOid`) or re-assigns it as its first line, as `sova/commands/data/commands/pr.md` and `sova/commands/data/commands/address-pr.md` do for `BASE`.
