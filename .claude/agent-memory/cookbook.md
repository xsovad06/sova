## Git Worktree Lifecycle

- **Git worktree stale registration recovery: prune + retry**. When a worktree directory is deleted externally (manual cleanup, process crash) but git's registration persists in `.git/worktrees/<id>/`, the next `git worktree add` fails with "missing but already registered" error. Defense-in-depth: (1) Always run `git worktree prune` before creating a new worktree (cheap ~5ms, negligible vs 200-500ms create time). (2) Detect the specific "missing but already registered" error after a failed create attempt, prune again, and retry once to handle race conditions. Mirrors pattern in `resolve_worktree_conflict()` and `cleanup_worktree()`. Implemented via `_prune_worktrees()` and `_add_worktree()` helpers in `sova/git/worktree.py:create_worktree()`, with a `worktree.stale_registration_recovered` log on successful retry. Issue #903 (hardening), run #2242 root cause. [confirmed: 1]
- **Worktree stash safety with shared stack: capture SHA, apply by SHA, drop by re-resolved index**: when worktrees share a stash stack (tracked via `git stash list`), never bare `git stash pop` — you could pop another session's changes and lose uncommitted work. Pattern: (1) capture your entry's SHA via `git stash list --format='%H %gs' | grep "<unique-tag>"`, (2) `git stash apply <sha>`, (3) re-resolve the entry's current index by tag (`idx=$(git stash list | grep "<tag>" | head -1 | cut -d: -f1)`), (4) `git stash drop "$idx"`. The index shifts as other sessions pop entries; always re-resolve before dropping. Session safety guaranteed if every concurrent agent uses a unique message tag. Discovered during PR #928 push (feat/authentication-ui-setup branch). [confirmed: 1]

## DB / Models

- **`TaskRun` uses `started_at`, not `created_at`** [promoted: full detail in `testing-patterns` skill]. [confirmed: 2]

- **Scope `TaskRun` queries by role when the function is role-specific**: a query filtering `issue_number + status` without a `role` filter can match a TaskRun from the wrong role (e.g., developer instead of researcher). When the caller's intent is role-specific (e.g., "find the researcher's awaiting_approval run"), add `TaskRun.role == "researcher"` to the WHERE clause. Without it, a newer non-researcher run shadows the intended target. PR #663. [confirmed: 1]
- **Add `id.desc()` as a deterministic tie-breaker in "most recent" queries**: `order_by(started_at.desc()).limit(1)` is non-deterministic when two rows share the same timestamp. Add `.order_by(TaskRun.started_at.desc(), TaskRun.id.desc())` so the highest auto-increment ID wins. Applies to any "find the latest X" pattern. PR #663. [confirmed: 1]

## LLM / JSON Parsing

- **Extract JSON from LLM responses using `raw_decode()` over regex/manual bracket-counting**: LLM responses often include prose before/after JSON, markdown code fences, or trailing text that causes `json.loads()` to fail with "Extra data" or "Expecting value" errors. Use `json.JSONDecoder.raw_decode(text, idx)` which correctly handles brackets inside quoted strings and returns `(obj, end_idx)`. For LLM responses without fences, scan left-to-right for `[` or `{`, try `raw_decode()` at each position, skip invalid positions, return the first valid JSON object. Fallback to empty string / None if no JSON found; log a warning instead of raising. Pattern: `extract_json()` utility in `sova/utils/json.py`. Applied to llm_suggestion_service, planner, oversight/analysis, generate_tasks. PR #870. [confirmed: 1]

## Testing

- **Tests that drive a daemon run loop must stub every LLM hook, not just the observe/record ones**: `tests/test_oversight_persona.py::TestOversightAgentPersona` patched `_observe`, `_record_run`, and `_interruptible_sleep` but left `_analyze` real, so each cycle spawned the actual `claude` CLI subprocess. It stayed green in CI (no `claude` binary, so the call fails fast and the cycle records an error) and only failed on developer machines, where two live calls blew the 30s `pytest-timeout` and cost real money. Symptom to grep for in a timeout traceback: a `shell.run cmd=('claude', '-p', ...)` line in captured stdout. When a test starts an agent loop, enumerate every awaited hook in the cycle body (`agent.py` `_observe`/`_analyze`/`_record_run`) and stub all of them; `tests/test_oversight.py` already had the correct `_noop_analyze(snapshot, run_id) -> ([], None)` pattern. Fixing it cut the suite from 100s to 78s. [confirmed: 1]
- **Mock process objects must expose `_proc` for shutdown handlers**: `_wait_and_finalize`'s CancelledError handler calls `agent.process._proc.terminate()` and `_proc.kill()` directly (not `process.stop()`) to avoid double-cancellation. `MockAgentProcess` in `sova/ipc/testing.py` needs a `_MockSubprocess` inner object with `terminate()`, `kill()`, `wait()` and `returncode`. Without it, shutdown tests fail with `AttributeError: 'MockAgentProcess' object has no attribute '_proc'`. Pattern: when production code bypasses the public API to access internal attributes for resilience, the mock must match. PR #620. [confirmed: 1]
- **Spawn mock functions must use `**kwargs` to absorb new parameters**: `async def _capture_spawn(prompt, cwd, env=None)` breaks when `spawn()` gains new kwargs (e.g., `output_dir`, `run_label`). Use `async def _capture_spawn(prompt, cwd, **kwargs)` and mock `_update_task_run_output_path` alongside `_update_task_run_pid`. File: `tests/test_dashboard.py`. PR #500. [confirmed: 1]
- **Integration tests needed for complex SQL correlated subqueries; unit mocks only verify behavior, not SQL correctness**: a unit test that mocks the DB count returned by a query (e.g., `_check_repeated_failures_gate`) verifies control flow but never executes the SQL. A correlated subquery like `SELECT count(*) WHERE id > (SELECT coalesce(max(id),0) WHERE status='done')` can have off-by-one boundary bugs or wrong column references that only appear with real rows. Add an integration test class with `sqlite+aiosqlite:///:memory:` and seeded `TaskRun` records covering: (1) failures before a success excluded, (2) failures since last success at threshold trigger block, (3) all failures count when no prior success. Use `yield` fixture teardown with `await engine.dispose()`. PR #473. [confirmed: 1]
- **Helper functions returning `object | None` should return concrete types when callers access specific attributes**: `_try_load_config()` declared `object | None` but callers access `.github_repo`. This hides attribute errors from static checkers. Return the concrete `ProjectConfig | None` type. For circular-import safety, guard the import with `TYPE_CHECKING`: `if TYPE_CHECKING: from sova.config.models import ProjectConfig`. The module must have `from __future__ import annotations` (or use string annotation `-> "ProjectConfig | None"`) so the runtime doesn't evaluate the annotation eagerly and raise `NameError`. PR #473. [confirmed: 1]
- **Functions locally-imported in a helper (`from x import y as z` inside a function) must be patched at the import source, not at the module**: `run_shell` imported as `from sova.utils.shell import run as run_shell` inside `_check_pr_branch_pushed()` creates a local name that `monkeypatch.setattr("sova.dashboard.services.agent_db.run_shell", ...)` cannot reach. Patch `sova.utils.shell.run` instead. PR #347. [confirmed: 1]
- **Direct unit tests for mocked functions, and except-block coverage for the SonarCloud gate** [promoted: full detail in `testing-patterns` skill]. PR #347, #400, #462, #817. [confirmed: 3] / [confirmed: 2]
- **`git reset --soft` must target the branch base, not `origin/main`**: if main has moved forward since the branch was cut, `git reset --soft origin/main` resets to a newer commit, leaving main's changes as unstaged modifications in the working tree. Find the parent of the first branch commit (`git log --format="%H" -1 <first_commit>^`) and reset to that SHA instead. When the branch already contains a `Merge branch 'main' into <feature>` commit (e.g., from an earlier rebase-conflict resolution), the correct target is that merge commit's second parent (`git log -1 --format="%P" <merge-sha> | awk '{print $2}'`), i.e. main's state *at merge time*, not today's `origin/main`. Resetting straight to `origin/main` in that case pulls in every unrelated main commit since the merge as spurious diffs, and the tell is `git status` after the reset showing files the PR's own commits never touched (README/AGENTS.md/CLAUDE.md doc churn from other people's merged PRs). Verify before recommitting: `git diff <second-parent> origin/main --stat` should list exactly those unrelated files. The general, simplest form of this check: `git merge-base HEAD origin/main` gives the actual fork point regardless of history shape (plain branch, rebased branch, or one with merge commits); reset to that SHA, never to `origin/main` directly, in the address-pr squash flow (step 8). If a reset against the wrong base produces a huge unexpected file list, `git reset --hard <backup-branch>` immediately restores the pre-reset state; recompute the correct base and redo the squash from there, but be aware the hard reset also discards any *uncommitted* fixes made since the backup was created (re-apply them from memory/diff before recommitting, then verify with `git diff <backup-branch>` that nothing was lost). Rebase onto the true current `origin/main` (step 9) only after the squash is complete, not as a substitute for finding the right squash base. PR #462, PR #928, PR #1002. [confirmed: 3] Related: worktrees can accumulate pre-existing uncommitted changes from prior agent sessions; `git reset --soft + git reset HEAD .` surfaces them alongside the commits' changes. Always run `git status` before starting a squash flow in an existing worktree. [PR #510]
- **Heuristic regex searches must be scoped to the relevant section, not the full document**: `_SOVA_VERDICT_LINE_RE.search(body)` in the heuristic fallback ran on the whole review body. General pattern: when scanning for a value that appears in a named section, split on the section header first. PR #400. [confirmed: 1]

- **Runtime/stress/chaos tests excluded from CI via pytest markers**: `tests/runtime/` uses `@pytest.mark.runtime`, `@pytest.mark.stress`, `@pytest.mark.chaos`. `make test-py` adds `-m "not runtime and not stress and not chaos"` to keep CI fast. `make test-runtime` runs only heavy tests with 120s timeout. - **Module-level cache requires `setup_method` in ALL test classes that call the cached function**: adding a module-level cache to a service function makes every test class that calls that function share state. Adding `setup_method` only to the new test class leaves existing classes vulnerable to poisoning from cache hits left by previous tests. Add `setup_method: clear_cache()` to every class in the file that invokes the cached function, not just the new ones. When changing a cache's type (e.g., `tuple | None` -> `dict`), grep ALL test files for the old reset pattern (`= None`) and update to the new one (`.clear()`); tests pass individually but ERROR in the full suite when one class corrupts the module-level variable for subsequent classes. PR #405, #595, #767. [confirmed: 4]
- **MagicMock `__truediv__` creates filesystem-illegal filenames when Path mock is evaluated**: if a `Path` is mocked and code evaluates `path / ".claude" / "sova.db"` during a test run, the result is a `MagicMock` object whose `str()` is literally `<MagicMock name='mock.__truediv__().__truediv__()' id='...'>`. If that string gets passed to `db_path.parent.mkdir()` or `open()`, Python creates a file with that literal name. These files must be deleted before committing and are easy to miss with `git add`. Fix: mock at a higher level (patch `list_projects` to return real `tmp_path` entries) so `Path.__truediv__` is never invoked on a mock. PR #430. [confirmed: 1]
- **MagicMock attributes default to truthy MagicMock objects; boolean-checked fields must be set explicitly**: `mock = MagicMock(); if mock.running:` takes the truthy branch because `mock.running` returns a new `MagicMock` (truthy). Tests gated on `obj.running == False` or `not obj.enabled` silently take the wrong path. Fix: always set boolean fields after construction: `mock.running = False`. Same applies to any field used in boolean context (`enabled`, `active`, `is_ready`). PR #819. [confirmed: 1]
- **`MagicMock(name="foo")` sets the debug repr, NOT the `.name` attribute**: `name=` is a reserved `MagicMock` constructor arg that controls the mock's display string (e.g., in tracebacks). To set the `.name` attribute, assign after construction: `mock = MagicMock(); mock.name = "foo"`. Tests that check `x in mock.name` or `mock.name == "foo"` silently pass for the wrong reason because `MagicMock.__contains__` defaults to `False` and attribute access returns a new mock. PR #418 CodeRabbit. [confirmed: 1]
- **`MagicMock().__truediv__()` leaks as literal filenames when evaluated against `Path.__truediv__`**: if a test helper creates a real SQLite file at a `Path` that is actually a `MagicMock`, Python evaluates `mock_path / ".claude" / "sova.db"` and returns a `MagicMock` whose `str()` becomes `"<MagicMock name='mock.__truediv__().__truediv__()' id='...'>"`. Any code that does `open(str(path))` or `sqlite3.connect(str(path))` will create real files with those names. Gate test helpers that create real files with `assert isinstance(path, Path)` or pass `tmp_path / "subdir"` explicitly rather than a mocked path. PR #443. [confirmed: 1]
- **Mock-based gate tests cannot verify correlated SQL subqueries: use a real DB**: `TestRepeatedFailuresGate` mocked `scalar_one_or_none()` to return a count, so the correlated subquery (`WHERE id > (SELECT max(id) WHERE status='done')`) was never executed. - **Avoid forward-anticipating dead code stubs in state maps**: adding dict/switch entries for states that don't exist yet (e.g., `_PR_STATE_ACTIONS["merged"]`, `prStateColor("merged")`) misleads readers into thinking those paths are exercised. - **A behavioral test that guards logic in another file must EXTRACT that logic, not re-implement it**: a test that hardcodes a copy of a workflow's shell `case` classifier (or any source-of-truth logic) is a false guard: if someone broadens the doc exclusion in the workflow, the copy stays correct and the test keeps passing, so the regression it claims to catch slips through. Extract the real block from the source at test time (e.g., anchor on `code="false"` ... `echo "code=$code"` in `sonarcloud.yml`, strip YAML indentation, run it in `bash -c`), asserting the anchors exist so extraction cannot silently degrade to matching nothing. Applies to any test whose docstring promises "exercises the same logic the CI does". Issue #857, PR #859 CodeRabbit. [confirmed: 1]
- **Structural tests that parse workflow/YAML blocks must tolerate trailing comments and match keys, not full lines**: a `_job_block` helper whose terminator required the next line to END with `:` broke on `  python-test:  # gated` (a key with a trailing comment), silently absorbing later jobs so an `if: always()` from a neighbor made the assertion pass for the wrong job. Match a 2-space-indented YAML key via regex (`^  [A-Za-z0-9_-]+:`) instead. Same principle for `count("needs: changes") >= 2`: a bare file-wide substring count is satisfied by prose comments or unrelated jobs; assert the declaration per job block instead. Issue #857, PR #859 CodeRabbit. [confirmed: 1]
- **A local `_init_repo()`-style helper that commits via `run()` (not `run_checked()`) without setting `user.email`/`user.name` first passes locally and fails silently in CI**: `git commit` on a dev machine succeeds without local config because git falls back to an OS-derived identity (real name + hostname) that CI runners lack, so `git commit --allow-empty` returns non-zero there. Since `run()` doesn't raise on failure, the repo silently ends up with zero commits, and a later `git rev-parse HEAD` fails with `fatal: ambiguous argument 'HEAD': unknown revision`. Every other test helper that inits a real repo (`test_workflow_timeout.py`, `test_worktree_deletion.py`) already sets `git config user.email`/`user.name` right after `git init`; a new helper must follow the same pattern or it passes locally and fails only on CI. PR #952.
- **A retry loop must rebuild any payload captured from mutable state before the mutating step, not reuse the pre-mutation value**: `ValidateStep`'s fix loop built `hook_stdin` (containing the current HEAD SHA) once before the retry loop, then reused that same value on every retry even though each retry follows an `invoke()` call that instructs the LLM to commit a fix (moving HEAD). The retry hook was fed the stale, pre-fix SHA instead of the new commit's SHA, so a hook that inspects the supplied `local_sha` would validate the wrong commit. Caught by CodeRabbit on a second manual review pass, not the first automated one. Fix: rebuild the payload (`build_pre_push_stdin()`) fresh on every loop iteration, right after the mutating call, not once outside the loop. General pattern: any retry/fix loop that captures state (a SHA, a timestamp, a file's mtime) before invoking something that changes that state must recompute it inside the loop for each attempt. Regression test pattern: make the mutating step (mocked `invoke`) actually perform the mutation (commit a real change in a real tmp repo) and assert the retry observes the post-mutation value, not just that the retry eventually succeeds. File: `sova/core/steps/validate.py`. PR #952 CodeRabbit.
- **Real-git fixture repos must also disable commit signing and hooks, not just set identity**: a helper that inits a real repo and sets `user.email`/`user.name` (per the #952 lesson above) can still block or fail on a machine whose global config sets `commit.gpgsign=true` or `core.hooksPath`. A non-interactive `git commit`/`git rebase --continue` in that fixture then hangs waiting on a passphrase prompt with no TTY (timing out at the pytest-timeout limit, not failing cleanly) or runs an unrelated hook script. Set both locally right after `git init`/`git config user.*`: `git config commit.gpgsign false` and `git config core.hooksPath <empty-dir-under-tmp_path>` (an explicit empty directory, not `/dev/null`, so the intent doesn't depend on how git treats a non-directory hooks path). File: `tests/test_rebase_verification.py:_build_conflicting_repo`. PR #966 CodeRabbit.
- **A test that directly enters the real FastAPI lifespan leaks global structlog config into every test that runs after it in the same session**: `create_app()`'s lifespan calls `setup_logging()` unconditionally at the top, which does `structlog.configure(...)` (a process-global call). httpx's `ASGITransport` never drives the ASGI lifespan protocol, so ordinary client-fixture tests never trigger this and it goes unnoticed; but a regression test written to actually exercise startup-loop logic (necessary here: a bug in the multi-project startup loop is invisible to any test that doesn't run the loop) must call `app.router.lifespan_context(app)` directly, which does run `setup_logging()`. The reconfigured structlog renderer then broke `caplog`-based assertions in an unrelated file (`tests/test_jira_adapter.py`) that ran later in the same pytest session, producing a failure that passed in isolation and only reproduced when the two files ran together (`pytest tests/test_dashboard.py tests/test_jira_adapter.py`). Fix: `with patch("sova.utils.logging.setup_logging"):` around the `async with app.router.lifespan_context(app):` block. General pattern: any test that enters a real app/service lifespan (not just an ASGI transport call) must audit that lifespan's startup code for global `configure()`-style calls (logging, structlog, warnings filters, `asyncio` event loop policy) and patch them out, then verify by running the new test file back-to-back with an unrelated file that uses the same fixture (`caplog`, `capsys`) to catch cross-file leakage that a solo run of either file would miss. PR #1002 (issue #921).

## Async / Concurrency

- **A per-key `asyncio.Lock` dict is a cheap, correct fix for a single-process validate-then-persist race**: `settings_service.update_config()` read the current config, validated a proposed change against it, then persisted, with no lock covering both steps. Two concurrent saves (e.g. `llm.provider="ollama"` and `llm.model=""`) can each validate against the same stale snapshot and both pass, jointly persisting an unloadable combination that then breaks every subsequent `load_config()` call. A `dict[str, asyncio.Lock]` keyed by resolved project path, with a lazy get-or-create helper (`_get_update_lock()`), closes this: the getter itself is race-free because there is no `await` between the `dict.get()` check and the `dict[key] = lock` assignment, so no other coroutine can interleave. This only serializes one process; it does not help if multiple dashboard processes share one DB, but that is not this project's deployment shape (one dashboard process per project). Regression test: run the two conflicting updates via `asyncio.gather()` and assert `load_config()` never raises afterward, plus assert at least one of the two results contains an error. Verify the test actually catches the race by temporarily swapping the shared lock for a fresh no-op lock per call (`patch.object(module, "_get_update_lock", lambda pd: asyncio.Lock())`) and confirming it now fails repeatedly (20/20 in this case) before trusting the test. PR #1002 CodeRabbit (issue #921).
- **`asyncio.shield(coro)` leaves the inner task detached and unobserved once the outer cancellation propagates**: wrapping a write in `asyncio.shield()` so cancellation can't abandon an in-flight transaction is correct, but `await asyncio.shield(coro)` implicitly does `ensure_future(coro)` and nothing keeps a reference to that task. If the outer awaiter is cancelled and the detached insert later raises (a *second*, independent failure after the shield already let the cancellation through), nobody observes the exception: no re-buffer, no log, and asyncio's own "exception was never retrieved" warning is the only trace. Fix: call `asyncio.ensure_future(coro)` yourself first, keep the `Task` handle, and attach `task.add_done_callback(...)` in the `task.cancelling() > 0` branch (the case where the shielded write is left running) so a later failure is logged and, where applicable, the batch is re-buffered. Files: `sova/core/output.py`, `sova/monitoring/writer.py`. PR #959. [confirmed: 1]

- **Oversight observation: compute `active_agents` from per-project running counts, not FleetInsights totals**: `FleetInsights.total_runs` is the all-time historical run count (sum of all rows in task_runs tables), not the count of currently-running agents. Mapping it to a field named `active_agents` yields a value in the hundreds or thousands on active installations. Correct approach: after `_collect_all_projects()` completes, compute `active_agents = sum(p.runs.running for p in snapshot.projects)`. This works because each per-project DB query already tracks `running` count separately from `total`/`done`/`failed`. PR #445. [confirmed: 1]
- **Oversight observation: status flags need `failure_reason` discriminator alongside boolean `timed_out`**: using a single `timed_out: bool` to cover asyncio timeout, DB operational error, and generic exception conflates three different diagnoses. Downstream consumers (analysis phase, operators) need to distinguish "slow project" from "misconfigured project" from "programming error". Pattern: keep the boolean flag for fast branching, add `failure_reason: str | None = None` with string constants (`"timeout"`, `"db_error"`, `"error"`) for each branch. PR #445. [confirmed: 1]
- **Background daemon subprocesses must have timeouts**: `await proc.wait()` without `asyncio.wait_for(proc.wait(), timeout=N)` in a daemon loop (oversight, supervisor, scheduler) hangs the entire cycle indefinitely if the subprocess stalls. Always add timeout + `proc.kill()` on `TimeoutError`. File: `sova/oversight/agent.py:_auto_triage()`. PR #585. [confirmed: 1]
- **Oversight observation: failed cycles must record ERROR status, not DONE**: if `_observe()` returns `None` and the wake cycle records `OversightRunStatus.DONE` with `snapshot=None`, a failed cycle is indistinguishable from a clean cycle. Record `OversightRunStatus.ERROR` when snapshot is `None` so operators can see in the DB that data collection failed entirely. PR #445. [confirmed: 1]
- **Use `json.JSONDecodeError` not `ValueError` for JSON parse failures**: `json.JSONDecodeError` is a subclass of `ValueError`, so both catch JSON errors. But catching `ValueError` in a block that also does arithmetic or string operations silently swallows unrelated errors. Always catch the specific subclass: `except json.JSONDecodeError`. PR #445. [confirmed: 1]

## Process / Subprocess Management

- **pytest-xdist `-n auto` can deadlock indefinitely, escaping step_hard_timeout**: validate step spawned `pytest tests/ -v -m "not runtime and not stress and not chaos" -n auto` as a subprocess. All 7 xdist workers hung at 0% CPU for 6.5 hours. The step_hard_timeout (1800s) wraps `asyncio.wait_for` on the step's `execute()`, but if the step delegates to a subprocess via `run()` (shell command), the timeout kills the `await` but does NOT kill the child process tree. The Python parent process (`sova run`) stays alive waiting on the subprocess `wait()`. Fix: subprocess timeouts must use `process.kill()` + `process.wait()` on `asyncio.TimeoutError`, not just cancel the coroutine. Also: consider whether `-n auto` is appropriate for CI validation (7 workers on a busy machine can deadlock on shared resources). Discovered: issue #597 developer run stuck for 7h 11m, PID 50048 -> PID 82221 (pytest). [confirmed: 1]

- **`task_queue` in git-tracked `sova.toml` is overwritten by PR merges**: the supervisor daemon correctly prunes closed issues from the on-disk queue via `_save_queue_to_toml()`, but these changes appear as uncommitted `M sova.toml`. When a PR that also touches `sova.toml` is squash-merged, the merge overwrites the daemon's pruned queue with the branch's stale version. The daemon re-prunes within one poll cycle (~240s), but the committed version remains stale. Root issue: runtime state (task_queue) should not be in a git-tracked config file. Issue #691 tracks moving to DB or gitignored file. [confirmed: 1]

- **Empty `list_tasks()` return can wipe entire queue**: `GitHubAdapter.list_tasks()` returns `[]` on rate limiting or API errors instead of raising. `_prune_done()` treats every queued item as "missing from open issues" and wipes the queue. Architecture doc says "if `adapter.list_tasks()` fails, the entire pass is skipped" but this only catches exceptions. Guard: `if not task_map: return queue` in `_prune_done()`. Issue #691. [confirmed: 1]

- **A blocking `subprocess.run` reached from an async entry point stalls the whole event loop, not just its own coroutine**: `sova/llm/client.py`'s config loader (`_config_root`) shells out to git (`_resolve_primary_root`, a blocking `subprocess.run` with a 5s timeout) whenever the caller's cwd is a worktree with no `sova.toml` of its own, which every pipeline step now does after routing was wired to load config unconditionally. Calling the sync loader directly from `invoke()`/`invoke_command()`/`invoke_batch()`/`invoke_streaming()` stalls the event loop (and any concurrent task's cancellation) for up to 5s per call. Fix: wrap the sync loader in `asyncio.to_thread()` behind an async wrapper (`_try_load_config_async()`) and await it from all four entry points. A CodeRabbit review flagged a first attempt that awaited it inside `asyncio.gather` alongside a decoy sleep, which passes even if the loop blocks, since `gather` waits for both regardless; the fix is a timing assertion measuring `first_tick_at - start` against a threshold well under the blocking call's duration. PR #985 CodeRabbit, issue #913. [confirmed: 1]

## Supervisor / Progression Engine

- **All finalization paths update DB but none touch GitHub labels (DB/tracker disconnect)**: `_wait_and_finalize()`, `recover_stale_runs()`, `_finalize_task_run()`, and WorkflowEngine all set TaskRun.status in the database but never call `adapter.transition_state()` or `adapter.remove_label()`. The issue stays stuck with `agent:in-progress` on GitHub while the DB shows `failed`/`interrupted`. The supervisor reads GitHub state, sees IN_PROGRESS, has no transition, and returns WAIT forever. Fix: #649 (reactive label rollback on finalization) + #650 (proactive supervisor reset for stuck issues). Rollback state is deterministic from `(role, pr_number)`: developer+no PR -> `agent:researched`, developer+PR -> `agent:in-review`, researcher -> `agent:triaged`, triage -> remove all labels. [confirmed: 1]
- **`task_queue` is an exclusive filter for supervisor evaluation**: the progression engine evaluates ONLY issue numbers listed in `task_queue`, in order. An empty queue means the supervisor evaluates nothing (by design: use `auto_queue = true` to populate it automatically each cycle). An old task_queue with stuck/done issues makes the supervisor appear completely idle. Diagnosis: check `sova.toml` `[supervisor] task_queue = [...]`. Fix: enable `auto_queue` to let `maintain_queue()` prune done issues and discover ready ones each cycle. [confirmed: 2]
- **Health check must not call list_tasks() to verify adapter**: `list_tasks()` fetches all open issues, making the health phase as expensive as the progression phase (2x API calls per cycle). If you need an adapter liveness check, use `adapter.get_task(known_id)` or omit it entirely and let progression's own error logging surface adapter failures. PR #453. [confirmed: 1]
- **supervisor_service queries need project_slug filter for PostgreSQL shared-DB**: SQLite single-project mode is isolated by file, but PostgreSQL deployments share one DB. Always add a `WHERE project_slug = ?` clause when querying `SupervisorDecision`. Router must load config to get `cfg.github_repo`; wrap in try/except since tests use `Path.cwd()` without a real sova.toml. PR #453. [confirmed: 1]
- **Router tests that assert on filtered data must mock load_config to match seed slug**: when router endpoints load config to resolve project_slug, tests that seed data with a fixed slug (e.g., "test/repo") must patch `sova.config.loader.load_config` to return that same slug. Without this, the router reads the real sova.toml ("xsovad06/sova") and the filter produces 0 results. PR #453. [confirmed: 1]
- **Researcher re-spawn loop: two compounding bugs, both must be fixed**: Bug A: `awaiting_approval` was in `TASK_RUN_TERMINAL`, so `_check_already_running` excluded completed researcher runs from its dedup query; the gate saw "no active agent" and re-spawned every 30s. Fix: `_ALREADY_RUNNING_TERMINAL = TASK_RUN_TERMINAL - {"awaiting_approval"}`, then block unconditionally on any `awaiting_approval` run (PID-liveness check does not apply). Bug B: `ResearcherRole.execute()` only called `transition_state(RESEARCHED)` on `success=True`; when the spec step paused for human review (`final_status=AWAITING_APPROVAL`), the GitHub label stayed as `agent:triaged` and the progression engine independently re-triggered research on the next poll. Fix: call `transition_state(RESEARCHED)` for both `success=True` and `final_status==AWAITING_APPROVAL`. Either bug alone causes duplicates; only fixing both closes the loop. PR #459. [confirmed: 1]

- **Dependency graph nodes carry only GitHub label state; agents page computes 21 distinct WorkItemStates**: `GET /api/dependencies/graph` nodes have `id`, `title`, `state` (GitHub label), `dependencies`, `available_actions` (static `_STATE_ACTIONS` dict). Missing: agent liveness, handoff pending, PR number, CI status, review verdict, last run failure. Supervisor drawer shows wrong available actions (e.g., "Integrate PR" when CI is failing). Pattern: in `dependencies.py:get_graph()`, after `graph.to_dict()`, batch-call `list_open_prs_with_state()` and `get_unified_agents()`, merge live state into each node keyed by issue number. `available_actions` must use `_get_actions(work_item_state)` not static `_STATE_ACTIONS[task.state]`. Also: `get_ready_tasks()` only unblocks when `dep_task.state == TaskState.DONE`, missing merged/closed issues — treat `stateReason == "MERGED"` as satisfying dependency too. Issues #481, #505, #507, #508. [confirmed: 1]
- **D3 forceLink crashes "node not found: N" when API returns edges to absent nodes**: `build_dependency_graph()` fetches missing dependency issues individually via `get_task()`; if the fetch fails (returns `None`), the issue is absent from `task_map` but still referenced in `_deps`, producing an edge in `to_dict()` with no corresponding node. `d3.forceLink(edges).id(d => d.id)` throws "node not found: N" and crashes graph rendering. Fix: filter edges in `to_dict()` to only include pairs where the target is a known task: `[e for e in self.edges if e[1] in self._tasks]`. Missing deps still appear in `validation.missing_refs`. PR #467. [confirmed: 1]
- **Tests calling `create_app()` without mocking load_config read the real sova.toml**: any test that calls `create_app()` without a project_dir reads the CWD's real `sova.toml`. When new config sections are added with non-default values (e.g., `[coderabbit_quota] enabled=true`), tests that assert disabled-state behavior break with assertion errors. Pattern: patch `sova.dashboard.routers.<router>.load_config` to return an explicit `ProjectConfig(...)` in every test that checks config-dependent endpoint behavior: not just filtered-data tests. PR #467. [confirmed: 1]
- **commit-format invariant must include all top-level sova/ directories as valid scopes**: when adding a new module directory (supervisor, mcp, monitoring, db, awareness), add the scope to `VALID_SCOPES` in `invariants/commit-format.sh` and to AGENTS.md's Scopes list. Missing scopes cause push failures even for obviously correct scope names. PR #345, #392. [confirmed: 2]
- **CHECKPOINT_NEEDED distinguishes "human approval needed" from "no action possible"**: must short-circuit before execution gates. PR #345. [confirmed: 1]
- **Evaluate_all should load config once and pass it through to gate methods**: avoids 2+ TOML parses per cycle. PR #345. [confirmed: 1]
- **Sync gates in asyncio.gather produce GC warnings**: use bare `return_value=` patching for sync methods, not `new_callable=AsyncMock`. PR #345. [confirmed: 1]
- **frozen=True on dataclasses does not freeze mutable field contents**: use `tuple`/`frozenset` for truly immutable fields. PR #345. [confirmed: 1]
- **Include PID-less nonterminal runs as active slot reservations**: `pid.isnot(None)` filter misses the creation-to-spawn window, allowing duplicate spawns. PR #345. [confirmed: 1]
- **`asyncio.wait_for(proc.communicate(), timeout)` does not terminate the subprocess**: cancelling the coroutine leaves the child process alive; repeated polls accumulate orphans. When the execution method delegates to `rollback_issue_state()` (which has its own concurrent-run guard), the primary path is safe. But fallback paths that call `adapter.transition_state()` directly need their own re-check, otherwise a dashboard-started agent between evaluation and execution gets its issue label overwritten. - **Do not cache transient API failures as negative results**: when a search function returns None for both "not found" and "API error", caching None on failure hides existing resources for the TTL window. - **Thread resolved project_dir through to fire-and-forget background tasks**: `asyncio.ensure_future` callees that independently resolve `get_project_dir()` or `Path.cwd()` may see a different project than their parent function. Pass `project_dir` as an explicit parameter to background tasks. File: `sova/dashboard/services/pr_service.py:_record_state_transitions()`. PR #767 CodeRabbit. [confirmed: 1]
- **Safety-critical gates must not trust "has data" as "completed successfully"**: `check_review_completed_gate()`'s `_has_reviewer_run()` checked only `has_sova_review` (does a verdict exist), not whether the underlying `TaskRun` actually finished (`status == "done"`). A failed or interrupted reviewer run can still carry `handoff_json` (crash after writing findings), so it satisfied the gate and allowed `SPAWN_INTEGRATE` on an unreviewed PR. Fix: expose the run's completion status alongside the verdict (`get_sova_review_verdict()` now returns `run_status`) and require it explicitly in the gate, rather than changing the shared query's status filter (which other display-only callers legitimately rely on). - **`patch()` a name where it is looked up at call time, not where it was originally defined**: a test patched `sova.llm.provider.create_provider`, but the function under test (`reload_provider()` in `client.py`) calls the bare name `create_provider(cfg.llm)`, bound via `from sova.llm.provider import create_provider` already executed at module import time. ## Architecture / Layering

- **Injected dependencies must validate not-None at construction time (fail-fast)**: when refactoring from a lazy import to constructor injection (e.g., `command_dispatcher` on `DAGExecutor`), add `if param is None: raise ValueError(...)` in `__init__`. Without this, `None` passes silently at construction and raises a confusing `AttributeError` deep in `_execute_node()`. Tests for the missing-argument case (`TypeError`) do not cover the `None` case. PR #783 CodeRabbit review. [confirmed: 1]
- **Import boundary AST tests should use `ast.walk()` for recursive checking**: `ast.iter_child_nodes()` only checks module-level imports; function-local `from sova.dashboard import X` bypasses the check entirely. Use `ast.walk(tree)` to recursively check all `Import` and `ImportFrom` nodes at any nesting depth. Also handle `SyntaxError`/`UnicodeDecodeError` explicitly (skip with warning) rather than swallowing silently with empty return. File: `tests/test_import_boundaries.py`. PR #783. [confirmed: 1]
